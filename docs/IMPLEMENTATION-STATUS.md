## PDF 生成的实际链路

实现分为解析、规划、写作、复核与发布，而不是把整份 PDF 一次交给模型。

- 先保存来源快照与文件哈希，使用 MinerU 获取带页码的块和图片。以原 PDF 的物理页数及非空页检查解析覆盖；没有精确页码的 Markdown-only 结果不能直接当作 PDF 证据。
- 图片使用视觉适配器识别，保存原图、派生解释与哈希。多面板页面另外渲染原始整页，将整页和裁切图一起核对，重新绑定证据，避免混淆独立演示或输入/输出。
- 所有可用块组成带偏移的 Unit 清单。每个处理窗口最多 32 个单元、约 18,000 个序列化字符；这是上下文预算，不是笔记数量上限。长文本完整分片，不静默截断。
- 模型为每个 Unit 作一个必填决定：纳入某主题，或说明排除原因。重复教学内容必须指向实际保留的内容。独立计划审查后，再跨窗口合并主题，保证每个局部主题恰好归入一个全局组。
- 根据统一写作规则生成章节，并通过必填的 Unit→章节映射检查遗漏。应用检查正文、资产白名单、数学语法与可执行的纯数字算式；独立模型审查事实、条件与覆盖。有界修订仍失败则进入 REVIEW，不拼接降级正文发布。
- 每篇原子笔记分别发布不可变 Revision，最后生成来源 MOC。发布检查来源当前性、候选哈希、活动政策、预期版本与任务租约。

超过当前全局摘要或单组写作预算的资料会明确停止，尚未实现递归的层级规划。图像联合核对目前按单篇笔记同页至少三个图片单元触发，不能覆盖所有跨页、双图或复杂表格关系。

实现入口：[生成编排](../services/noodle/src/noodle_agent/next/generation.py)、[解析](../services/noodle/src/noodle_agent/next/parsing.py)、[规划契约](../services/noodle/src/noodle_agent/next/generation_contracts.py)、[图像上下文](../services/noodle/src/noodle_agent/next/visual_context.py)、[写作规则](../services/noodle/src/noodle_agent/prompts/next_writing.v1.md)。[生成 JSON Schema](./schemas/next-v1-generation.schema.json) 描述可移植结构；运行时还会按当前 Unit ID 生成必填属性，来源与语义约束仍由应用检查。

## 首份真实课件的验证

使用用户指定的 59 页神经网络课件，完成原 PDF 冷解析。经用户明确授权，完整 PDF 发往 MinerU、课件图片发往当前豆包视觉服务、解析内容发往 DeepSeek。未使用旧笔记作为新正文输入。

本次得到 488 个来源单元，其中 365 个纳入正文，123 个按计划排除；生成 22 篇原子笔记和 1 份来源 MOC。排除内容保留理由与覆盖清单，不能将这个比例解释成教学内容丢失率或模型质量分数。未生成 Concept 或新检索索引。

真实试跑暴露并修复了以下问题：

| 问题 | 处理 |
| --- | --- |
| 分配的双列表互相冲突、长回答漏填单元 | 改为每个单元必填的单一决定与章节映射，应用核对全集 |
| 模型返回无效 JSON 或额外字段 | 留存原响应和失败回执；有界修订；不覆盖成功检查点 |
| 图片路径、LaTeX 代码反引号或非法命令 | 资产白名单、格式门禁及真实 KaTeX 编译 |
| 将不同卷积演示的矩阵混合，算式结果错误 | 原 PDF 整页复核；纯数字算式使用受限 AST 计算校验 |
| RGB 输入矩阵被当作输出 | 整页加裁切图重新识别，替换旧派生解释并建立新的页码证据 |
| 将未识别信息当作资料不存在、补出无依据推论 | 收紧统一写作与独立审查规则，保存明确修订反馈 |
| 已修订版本恢复时误用首次发布回执 | 恢复检查点绑定当前活动 Revision；验证修订发布后崩溃重跑及未变化 MOC |

确认错误的活动版本立即撤回，旧正文与报告保留；修订在同一 Note 身份下生成新 Revision，不删记录后重建身份。任务成功后发现错误可重新打开，并记录撤回及显式恢复原因。

工程回读检查活动版本、正文与候选哈希、发布回执、来源单元覆盖、图片存在性、KaTeX 和显式数字算式。KaTeX 只验证可渲染性，算式检查只覆盖受限的字面量表达式，均不能证明符号推导或图片解释正确。模型审查之外，已对反向传播问题种子及卷积图例做原文抽查；这不是 RAG 问答验收，也不是独立人工全篇验收。

## 恢复与错误处理

`next_0004` 保存每个阶段的输入哈希和不可变回执。解析提交前先登记 INTENT；如果远端是否接收无法确认，就停下等待核查，避免重传。解析轮询不消耗错误重试次数。成功解析、视觉结果、计划和已经发布的笔记都可恢复。

网络错误按任务预算重试；质量错误进入 REVIEW，需检查原因后显式恢复。Worker 有独立租约令牌和心跳，失去所有权不能发布。阶段缓存与请求、模型配置、Schema、提示及修订反馈绑定。模型与视觉调用保存时间、用量和哈希，失败响应留在本地审计目录。

## 现在可使用的命令

在项目根目录、已安装项目依赖的 Python 环境执行。真实生成需要 `.env` 配置的 MinerU、视觉与模型服务；数学检查需要可用的 Node.js。示例中的课件路径自行替换：

```sh
python -m noodle_agent.cli next-init --data-dir ./data/noodle-next
python -m noodle_agent.cli next-ingest --data-dir ./data/noodle-next --pdf "/path/course.pdf"
python -m noodle_agent.cli next-worker --data-dir ./data/noodle-next
python -m noodle_agent.cli next-status --data-dir ./data/noodle-next
python -m noodle_agent.cli next-verify --data-dir ./data/noodle-next --job-id JOB_ID
```

`next-worker --once` 处理一次领取，解析尚在轮询时返回 PENDING；质量停止或重试状态返回非零退出码。检查 REVIEW 原因后可恢复：

```sh
python -m noodle_agent.cli next-retry --data-dir ./data/noodle-next --job-id JOB_ID --reason "已核查并修复的原因"
```

支持人工决定后的重建与取消命令；本次按用户要求没有继续执行完整重建：

```sh
python -m noodle_agent.cli next-rebuild --data-dir ./data/noodle-next --job-id JOB_ID --reason "重新生成的明确原因"
python -m noodle_agent.cli next-cancel-rebuild --data-dir ./data/noodle-next --job-id JOB_ID --reason "取消并恢复原完成结果"
```

取消会撤销该任务的发布租约，但不能撤回已经发往外部服务的请求；操作前停止对应 Worker，可避免继续产生无用的外部调用。完成状态恢复的是重建前的结果，`rebuild_cancellation` 记录取消事实，不表示重建成功。

`next-schema` 输出运行时内容契约。恢复工具 [rebuild-baseline.py](../scripts/rebuild-baseline.py) 提供 create/verify/restore，要求新的输出目录，拒绝与原目录相互包含。

这些命令不会将默认前端切到新库。原业务库计数仍与基线一致：10 个来源、23 个来源版本、1,180 篇原子笔记、1,185 个笔记版本、809 个 Concept、1,634 个 Concept 版本、21 个任务。
