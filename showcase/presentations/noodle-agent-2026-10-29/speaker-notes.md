# Noodle Agent：演示逐页讲稿

## 01 · 01 / 开场 · Noodle Agent

大家好，我介绍的项目是 Noodle Agent。它基于 DeepSeek Harness，面向个人长期积累的教材、课件和论文。用户上传资料以后，系统先生成可独立阅读、带来源的笔记，再把不同资料对同一知识对象的描述归并起来，支持后续更新和引用问答。

我主要实现了文档到知识的 Workflow、知识身份和贡献模型、版本证据、检索引用与任务恢复。本地指知识和任务状态保存在本地，解析和模型推理仍使用配置的外部服务。接下来先从实际痛点和我实现的知识流程讲起。

## 02 · 02 / 项目背景 · 资料越积越多，知识却越来越难维护

做这个项目的起点是我学习同一主题时，经常要在教材、课件和论文之间来回切换。它们有重叠，也有各自独有的推导、图示和条件。文件越多，搜索和整理越费时间，而且一次问答结束以后，得到的知识未必沉淀成能继续维护的内容。

所以我把目标定为长期整理与更新：先让每份资料变成可读笔记，再判断跨资料的知识身份和增量。这样用户能直接阅读，加入新资料也能继续演化。下面这张图是完整的知识生成主线。

## 03 · 03 / 知识演化 · 从资料导入，到持续演化的知识

从左到右看，系统先登记PDF 的来源版本，使用 MinerU 解析或经过校验的兼容缓存，再按资料类型规划主题。必要时补视觉证据，随后写作、有限审查并发布 Atomic。Atomic 发布是一个关键边界，用户这时就可以开始阅读。

后面分成两条派生路径：一条负责索引与浏览，另一条负责 Concept 归属、构建和结构维护。目录组织不是向量构建的前置条件，也不要求用户等到全部维护结束。要理解这套流程，先区分三个不同的数据粒度。

## 04 · 03 / 知识演化 · 三种粒度，分别服务阅读、演化与检索

这里最容易混淆的是把它们都理解成切片。Atomic 是一份资料里的综合主题笔记，可以包含多个小节，跨多页保留完整推导。Concept 则代表跨资料长期维护的对象，比如支持向量机，内部再组织硬间隔、软间隔和核方法。

Chunk 才是检索范围，它从已发布的 Atomic 或 Concept 正文中切出，保存修订、小节和偏移。一个粒度服务阅读，一个服务知识演化，一个服务召回。下面先看 PDF 怎么变成 Atomic。

## 05 · 03 / 知识演化 · PDF 如何生成 Atomic 笔记

生成时先保留来源身份和来源版本，避免同名文件误命中缓存。解析结果带有正文块、标题、公式、图片和页码。规划不是一页生成一篇，而是按资料类型组织完整主题：教材参考目录，课件聚合同一对象，论文突出方法、实验和限制。

每个写作单元只带入相关证据和必要上下文，生成结构化小节后检查引用与资源，再发布不可变修订。note_id 保持稳定，revision_id 标识一次正文快照。接下来是这条流程里质量和成本之间的具体取舍。

## 06 · 03 / 知识演化 · 规划用 Pro，写作与有限审查用 Flash

模型分工里，Pro 和 Flash 是路由角色，实际模型看运行配置。前期规划一旦分错，后面写作和审查都会付出额外成本，所以优先把能力用在主题边界。常规写作已有较明确的输入约束，交给 Flash。视觉只在图表或解析缺失时使用。

审查采用一次 Flash 审查，有意见再修复一次。之后做结构、引用和资产检查，局部格式问题最多再恢复一次。这个选择降低循环修复成本，但不保证消除事实错误。下一页可以看到这些步骤最终形成的阅读界面。

## 07 · 03 / 知识演化 · 一篇 Atomic，保留完整的阅读上下文

这页用内容结构示意说明 Atomic 的阅读粒度。主题可以跨页，包含摘要、定义、适用条件、公式和实例；每个小节再关联来源版本与页码。它的目标是保留阅读上下文，不按页机械切分。示意展示数据组织方式，不是实际工作台截图。

阅读目录是导航投影，目录项不等于一定对应一篇 Atomic。用户可以在笔记发布后开始阅读，索引和跨资料维护继续推进。笔记发布、索引就绪和 Concept 完成要分别判断。看完单份资料，下面继续介绍多份资料怎样共同维护一个知识对象。

## 08 · 03 / 知识演化 · 跨资料归并：先确定对象，再判断贡献

Concept 的难点是对象身份和内容增量要分开判断。系统先读取当前有效 Atomic 并冻结版本，结合已有绑定、名称、别名、边界和核心覆盖构造候选，再判断应该复用、建立新对象，还是保留待解决状态。主批量归属并不是直接照搬问答的向量检索。

确定对象以后，再分配小节和内容贡献。签名不变就避免重复维护；有增量只更新受影响主题。发布还要重查来源、版本、目标代次和租约，防止旧任务覆盖新状态。接下来用贡献类型说明为什么新增资料不一定要重写正文。

## 09 · 03 / 知识演化 · 新来源进入后，不一定重写 Concept

这张表是知识演化里比较重要的设计。新增来源不等于新增正文。如果它补充了推导，就是核心增量；如果只是再次支持已有定义，就增加支持记录并尽量复用正文。深入阅读、判断上下文和冲突也有各自的处理方式。

例如 SVM 已经有教材和课件共同支持，删除课件以后，应重新计算剩余支持，而不是直接删除整个对象。图片还有独立贡献逻辑：文字没有变化，新资料仍可能提供更清晰的架构图。下一页结合实际工作台看知识对象和来源如何呈现。

## 10 · 03 / 知识演化 · 一个知识对象，保留多份来源的支持

这页用支持向量机的结构示例说明跨来源维护。教材、课件和论文可以提供不同内容，也可能只是重复支持。Concept 保持一个稳定身份，内部再组织硬间隔、软间隔和核方法，每项支持都关联具体的 Atomic 版本。示例不代表本轮重新生成或截图验收。

如果撤回一份来源，系统重新计算剩余支持，不能直接删除仍然有教材支持的整个对象。知识体系里的显示位置又是另一层阅读投影，一个对象有多个入口也不需要复制正文。接下来介绍承载这些领域能力的 Agent 架构。

## 11 · 04 / Agent 框架 · Agent 与知识服务如何连接

整体架构分成会话运行时和知识领域服务。Web 工作台的助手通过会话桥接进入 DSH 原生 Agent Loop，工具经过类型化契约和写操作审批，再通过统一的 TypeScript HTTP Provider 调用 FastAPI 的 internal/next 接口。

Python 服务维护知识、版本、证据和任务。SQLite 保存身份与状态，本地文件保存不可变正文、资产和检查点；独立 Worker 运行耗时步骤。选择 Harness，是复用成熟的循环、会话和审批机制，把主要实现精力放在这些领域能力上。

## 12 · 04 / Agent 框架 · 复用 Harness，把精力集中在领域能力

这里我会明确哪些是复用，哪些是自己实现。Harness 提供模型调用、会话历史、工具循环、审批以及上下文管理。我接入和设计领域工具，让这些工具访问可验证的知识状态，而不是让外层模型自己猜测任务是否完成。

我主要做的是知识 Workflow 和数据模型，以及围绕它们的检索、溯源和恢复。这样修改会话模型不会改变知识版本规则，修订笔记也必须经过领域服务。这个边界落实到实际接口，就是下一页的十七个工具。

## 13 · 04 / Agent 框架 · 17 个工具：把领域能力变成明确契约

当前工具总数是十七个，十三个只读、四个审批写。只读能力覆盖问答、搜索、笔记读取、目录关系以及任务状态。写工具包括修订小节、刷新结构、暂停和恢复任务。它们现在都走统一 HTTP Provider，不再有两套分散的业务访问方式。

设计工具时我更关注参数范围、返回状态和版本约束。例如先确认知识就绪，再做问答；读取目标小节以后，再提出修订。工具不能只返回一段自然语言成功提示。下面用小节编辑说明一次受控写操作。

## 14 · 04 / Agent 框架 · 一次小节编辑，经过版本与审批边界

以编辑一个小节为例，Agent 需要先读取目标和当前修订，形成范围明确的修改，再进入写操作审批。审批通过以后，也不是直接覆盖正文，而是由领域服务检查当前状态和版本，发布新修订，并触发相应索引和依赖维护。

如果审批期间其他任务已经改变了输入，旧结果不能无条件落盘。这种设计把会话里的意图和知识库里的事实写入分开。暂停、恢复和结构刷新也遵循明确工具边界。说完工具，再看长对话和长期知识分别由谁保存。

## 15 · 04 / Agent 框架 · 会话记忆、工具上下文、长期知识分层管理

项目里的记忆分成三层。第一层是会话历史，由 Harness 保存和压缩；第二层是工具结果，按需读取，较大的结果可以在上下文压力下裁剪；第三层才是长期知识，保存在领域服务管理的正文、版本、贡献和证据里。

所以对话压缩不会等同于删除知识。当前工具裁剪阈值预设为八千一百九十二字符，保留头尾，但要在上下文压力等条件下触发，不能说每次输出都会立即裁剪。接下来进入检索部分，看这些长期知识怎样变成可引用的回答。

## 16 · 05 / 检索与溯源 · 索引建立在当前有效的笔记修订上

索引的输入是当前有效的 Atomic 和 Concept 修订。系统按小节和正文范围生成 Chunk，保存笔记、版本、小节、偏移和文本 hash，再分别构建全文和向量索引。Chunk 不是丢掉来源以后的一段孤立文本。

当前记录的向量 profile 是 text-embedding-v4、一千零二十四维、ExactVectors，实际运行仍以配置和就绪结果为准。缓存和索引需要匹配 profile，不能混用。建立索引以后，问答会同时利用词项匹配和语义匹配。

## 17 · 05 / 检索与溯源 · 混合检索如何变成引用回答

一次问答先检查知识就绪状态和来源范围。全文检索适合明确术语，向量召回补充语义相近内容，之后融合、去重并组织有界证据。回答必须依据符合当前有效性条件的片段，不能无条件使用历史索引命中的文本。

在 DSH 中，普通回答可以调用 answer 工具完成这条链路，工具结果再交给 Harness 输出。非 READY 时应说明状态并结束；继续任务需要明确意图。已有验收覆盖过 HYBRID READY 等情形，本轮主要验证展示。下一页看引用如何返回 PDF。

## 18 · 05 / 检索与溯源 · 引用沿版本与证据，返回原 PDF

这页展示原文定位的证据链。回答中的引用先关联命中片段，再找到笔记修订、小节和正文范围，沿来源证据返回特定版本的 PDF 和页码。原件 hash 区分同一资料的不同版本，避免修订以后引用漂移。这里是定位机制示意，不是 PDF 截图。

这条链路让用户能够查证，但引用存在并不代表结论必然正确。仍需核对证据是否真正支持陈述，尤其是公式前提、适用条件和跨来源归纳。可靠问答还依赖状态变化后的有效性管理，下一页接着讲删除、修订和索引怎样联动。

## 19 · 06 / 任务可靠 · 撤回内容后，先阻止旧知识继续被召回

删除不能只理解为删掉一个文件。首先要让笔记和对应 Chunk 失去当前检索资格，阻止旧知识继续进入回答，再重建或更新索引。旧向量、正文和缓存可能作为历史保留，所以不能把这里描述成所有副本马上物理清除。

同时，系统沿贡献依赖重新计算 Concept。如果还有其他有效来源支持，就维护剩余内容；输入发生变化，旧任务的发布条件也会失效。这解决的是业务有效性的一致性。接下来讲独立 Worker 如何在中断之后继续推进。

## 20 · 06 / 任务可靠 · 任务中断后，从可信阶段恢复

耗时流程交给独立 Worker，HTTP 不需要一直等解析和生成完成。Worker 领取租约并续租，提交时核对租约、输入版本和目标代次。这样旧执行者即使晚返回，也不能覆盖当前结果。重复事件则通过幂等键和输入签名减少重复发布。

恢复时使用阶段产物和检查点，但文件存在不代表可信，还要核对来源、配置与冻结 profile。暂停、失败、进程退出都需要能解释的状态。最后看成本：我主要从并发调度、模型路由和上下文约束三个方向优化。

## 21 · 07 / 成本优化 · 用并发、模型分工和上下文约束控制成本

成本优化主要有三类。并行和缓存减少重复等待与重复计算，但共享发布状态仍要受控。模型按操作分工，让规划承担较强模型成本，常规写作与审查使用 Flash。输入只给相关证据，候选和输出结构也要有边界。

历史固定四份 PDF 的对照里，文本 token 从九十九万多降到五十九万多，减少约百分之四十点五；调用数从一百八十五到一百二十五。这是特定历史样本，不能直接推广成费用或质量结论。下一步仍要把质量和合并规则评测补齐。

## 22 · 08 / 问题与扩展 · 先提高知识质量，再扩展音视频输入

当前还有两块需要继续打磨。第一是知识质量，包括遗漏、公式条件、图像证据和引用支持程度。第二是合并规则，怎样稳定地区分同一对象、内部变体和使用关系，怎样处理冲突和作者修订，需要更多可复现案例和回归评测。

后续我想扩展到视频和音频的笔记识别：先把时间戳、转写和关键帧作为新证据，再接入已有 Atomic、Concept 和版本维护链路。这部分目前是规划。项目当前最有价值的积累，是把生成、更新和查证连接成可持续维护的流程。

## 23 · 附录 / 工具契约 · 只读工具清单

这页是用于追问的只读工具完整清单。问答和搜索分开，读取完整对象和浏览目录也分开，避免每一次请求都返回过大的上下文。get_readiness 让 Agent 先了解当前索引和知识是否可用，任务与来源工具则提供可解释的进度。

这些工具共同走统一的 TypeScript HTTP Provider，业务状态仍由 Python 判断。工具名称本身不代表返回数据足够，参数、范围、版本和结构化状态才是契约的核心。涉及改变状态的能力放在下一页，单独经过审批。

## 24 · 附录 / 工具契约 · 四个写工具都需要审批

这四个工具覆盖小节编辑、结构维护以及任务控制。它们都经过写操作审批，但审批只是确认意图，后面仍需要领域服务核对版本和当前状态。工具应明确返回已发布、已提交任务或无法执行，而不能把请求受理都写成操作完成。

暂停和恢复尤其需要区分任务记录与进程执行。恢复沿用原任务冻结的配置，检查已有阶段结果，再继续运行。这样外层对话保持简单，内部业务约束仍然完整。面试追问时，我会结合具体工具参数和任务状态进一步解释。

## 25 · 附录 / 任务状态 · 任务进度和知识就绪，分别判断

这页把任务进度和知识就绪分开说明。笔记发布代表正文已经可以阅读；索引就绪代表当前有效修订能够参与检索；知识维护完成则对应跨来源贡献和结构更新。它们不是一个总体完成图标可以替代的状态。这里展示机制，不是实际任务截图。

用户应该能知道当前可以阅读什么、哪些内容可以检索，以及后台还有什么没有结束。任务提交成功也不等于维护已经完成。关于 Worker、租约和恢复的结论来自当前源码与已有记录，异常注入和端到端恢复一致性仍需要持续回归。

## 26 · 附录 / 事实边界 · 实现范围与验证边界

最后把事实边界集中放在这里。已经具备的是 PDF 到笔记和知识对象的链路、版本证据维护、DSH 工具接入，以及检索和任务恢复机制。需要继续验证的是内容质量、复杂合并、异常恢复一致性和引用交互。音视频输入仍是后续计划。

本次演示以十月二十九日项目介绍、当前代码和已有验收记录为依据；我们优化版式并验证演示文件，没有重新执行全量模型评测。因此展示实现能力时，我会把设计、已有验证和未来目标分别说清楚，避免把计划或历史样本当成当前完整结论。
