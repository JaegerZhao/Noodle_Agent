## 附录 A：只依据本文讲解项目

### A.1 精简开场

我做的项目是 Noodle Agent，一个基于 DeepSeek Harness 的可溯源本地个人知识管理 Agent，主要解决多文档知识整理、持续更新和可靠问答。

它先把教材、课件和论文 PDF 整理成带来源的 Atomic 主题笔记，再把不同资料对同一对象的内容维护成 Concept。问答从这两类笔记的当前版本生成检索片段，融合关键词和向量召回，返回能够追踪到原 PDF 的引用。

我主要实现了这套知识 Workflow、身份与贡献模型、版本证据、检索和任务恢复。Harness 负责会话、外层模型与工具循环，我通过 17 个领域工具接入 Python 服务，其中 4 个写操作需要审批。

项目里比较重要的设计，是把阅读笔记、跨资料知识对象和检索片段分开，并把来源变化传播到内容与索引。长任务由独立 Worker 执行，依靠租约、幂等和检查点恢复。接下来我可以沿知识生成、Agent、RAG 和可靠性四条链路展开。

### A.2 约 10 至 15 分钟的完整讲述稿

#### 开场与背景

这个项目来自我学习时同时阅读教材、课件和论文的需要。教材提供框架，课件有推导和图示，论文有方法和实验。资料积累以后，我需要频繁切换文件，也很难判断一份新资料到底补充了什么。

所以我希望先形成可以阅读和持续维护的知识，再支持问答。用户上传 PDF 后，可以先读已发布笔记；后台继续做索引和跨来源维护。我的主要实现集中在知识 Workflow、数据模型、检索证据和任务恢复，通用对话运行时使用 DeepSeek Harness。

#### 知识流程与内容粒度

结合总流程图，我会先讲三个粒度。Atomic 是一份资料内的完整主题笔记，可以跨页包含多个小节、公式和图片；Concept 是跨资料的稳定对象，例如支持向量机，内部再组织软硬间隔、核方法等主题；Chunk 是它们已发布正文中的检索范围，保存版本、小节和偏移。

这三个粒度分别服务阅读、知识维护和检索。身份与版本也分开：笔记 ID 稳定，修订标识一次不可变正文，来源证据保存 PDF 版本、页码和 hash。这样正文更新以后，旧版本和新版本仍然可以区分。

#### Atomic 怎样生成

PDF 先登记来源版本，再经 MinerU 解析。规划会识别资料类型，教材按可信目录分批，课件聚合连续主题，论文围绕方法、实验和限制组织。每个写作单元只带相关来源和必要上下文，再生成结构化小节。

模型按环节分工，规划和身份判断优先用 Pro，常规写作与 Section 审查主要用 Flash。审查一次，有意见修复一次，然后检查结构、引用和资源，局部格式恢复也有次数限制。视觉只在图表或文本缺失时按需使用。这降低了重复生成成本，同时仍需要独立质量评测。

#### Concept 怎样演化

归并先判断对象身份，再判断内容贡献。比如课件和教材都讲 SVM，它们可以支持同一个 Concept；但方法使用某个概率分布，并不意味着两者要合成一个对象。

新资料如果补上了推导，就更新对应主题；如果只是重复定义，就增加支持并复用正文；深入阅读、上下文和冲突分别记录。文字和图片也分别判断贡献。输入签名不变时跳过重复构建，真正发布前检查输入版本与目标代次。

如果撤回课件，系统重算剩余支持，而不是直接删除仍有教材支持的整个 SVM。知识体系和关系是阅读组织，一个对象可以有多个入口，共用正文。当前图主要服务浏览和维护。

#### Agent 架构与工具

结合系统图，资料阅读直接访问知识 API，对话通过会话桥进入 Harness，再调用领域工具。Harness 处理 Session、模型与工具循环、审批和压缩；Python 服务维护知识状态、RAG 和发布规则；Worker 执行耗时任务。

当前是 13 个读取类工具加 4 个审批写工具，统一走 TypeScript HTTP Provider。编辑时先读目标小节和版本，审批后服务端仍检查基准版本；如果期间别人更新了正文，就返回冲突并重新读取。会话历史、工具上下文和长期知识也分开保存，对话压缩不会删除知识。

#### 检索、回答与原文溯源

以比较 SVM 软硬间隔为例，先确定全库、指定来源或指定笔记范围。指定来源时只用其 Atomic，避免跨来源 Concept 带入其他资料。Chunk 按小节和正文范围构建，记录修订与证据，向量缓存绑定内容 hash 和 Embedding profile。

查询同时做 FTS5/BM25 和向量召回，再用 RRF 融合排名，按配置重排，补上下文、合并重叠并控制单笔记份额。回答依据有界证据包生成，随后检查支持、引用和内容当前性。

引用沿笔记修订、小节、偏移和来源证据返回 PDF 版本及页码。普通 answer 工具内部已经包含 RAG，默认返回领域答案后结束回合，减少外层模型再次改写。一次工具调用内部仍可能有多次模型请求。

#### 删除、并发与恢复

可靠性主要围绕状态变化。删除先让内容失去当前检索资格，再重算 Concept 支持和维护索引；历史文件和缓存由单独策略管理。

任务进入持久队列，由 Worker 领取限时租约并续租。Worker 中断后，新执行者校验冻结配置和检查点，继续未完成阶段。旧执行者迟到提交时，需要经过租约、版本、签名和代次检查。幂等控制重复派发、阶段复用和发布，但远端回执丢失仍可能带来重复调用，所以还要限制重试并记录回执。

#### 成本、结果与后续

成本方面，并行主要减少等待，Token 优化来自主题规划、局部上下文、批量候选、贡献增量、缓存和有限修复。历史固定四份 PDF 的文本 Token 从 996,515 降到 592,536，减少约 40.5%；这只是特定样本，没有完成独立质量 A/B，不能直接推广为费用或通用收益。

接下来优先完善知识质量和合并评测，包括条件与公式覆盖、引用支持、错合并和导入顺序。音视频是后续方向，通过转写、时间戳和关键帧建立证据，再复用 Atomic、Concept 与版本维护流程。

## 附录 B：常见追问与回答口径

### 1. 为什么要有 Atomic 和 Concept 两层？

Atomic 保留一份资料内的完整阅读上下文，Concept 维护跨资料的对象身份与增量。它们处理不同问题：来源内组织相对稳定，跨资料归并则会随新增支持持续变化。检索片段再从两类已发布正文中生成。

### 2. 为什么不只保留 Chunk？

Chunk 适合召回和上下文控制，但用户阅读、作者修订、来源归并需要更稳定的内容对象。项目因此把 Chunk 作为正文的检索范围，保留回到修订和小节的定位，权威内容仍由笔记版本管理。

### 3. Concept 判断依据是向量相似度吗？

当前主批量归属使用已有绑定、名称、别名、对象边界和覆盖情况构造有界目录候选，再由模型判断。身份判定与问答召回是不同任务。后续可以评估身份向量召回补候选的收益，但需要检查错合并与遗漏。

### 4. 新资料与旧内容重复时怎么处理？

用 `SUPPORT_ONLY` 增加来源支持，尽量复用已有正文；真正新增知识进入 `CORE_DELTA`。输入签名不变时跳过重复维护。图片独立判断贡献，避免文字重复时丢掉更有价值的图示。

### 5. 两份资料冲突怎么办？

保留条件差异、冲突属性和证据，不因为资料更新就直接覆盖旧结论。构建时区分核心增量、支持和争议，作者修订也有独立属性与保护规则。复杂冲突的准确处理仍需要更多案例评测。

### 6. 模型审查为什么不循环到没有意见？

多轮审查可能反复引入新意见，造成成本上升和无效修改。当前采用一次 Section 审查、一次定向修复，再做结构与引用等检查。这个选择保留质量风险，需通过抽查与独立标注评测判断效果。

### 7. 为什么规划用 Pro、写作用 Flash？

规划和身份判断会影响很多后续步骤，边界错误的传播范围更大。常规写作已有主题、局部来源和输出结构约束，因此主要使用 Flash。实际路由由策略与回执确认，特定恢复和其他模式也有相应规则。

### 8. Harness 具体替你完成了什么？

它提供 Session、外层模型与工具循环、审批、取消及上下文管理。我实现知识领域工具和 Provider 接入，Python 负责知识生成、版本证据、RAG 和任务恢复。会话桥只适配协议与约束范围。

### 9. 为什么 answer 不先 search？

`answer_knowledge` 已包含完整检索和回答检查。普通问题先 search 再 get 会重复组织证据，也让外层模型承担额外事实综合。需要查找或检查材料时使用 search，普通问答直接调用 answer 并返回领域结果。

### 10. 如何防止 Agent 修改错笔记？

先通过发现与读取工具拿到真实笔记、小节和版本身份，写操作再经过审批。服务端继续检查 `expected_revision` 和状态，冲突时重读。审批、身份核对与版本约束分别承担不同保护作用。

### 11. 这里的记忆与向量库是什么关系？

对话历史由 DSH Session 保存，上下文可以压缩；长期知识由 Atomic、Concept、版本和证据维护。向量是长期正文的可重建检索投影。新问题的事实依据来自当前有效工具结果，不能只复述旧会话答案。

### 12. 为什么用 RRF？

关键词与向量的分数尺度不同，直接相加需要额外标定。RRF 根据每路排名贡献分数，便于融合不同召回路线。融合后仍可重排，最终收益需要通过固定问题集比较召回和答案质量。

### 13. 向量模型或维度改变怎么办？

Embedding profile 与缓存、索引绑定，不兼容时不能混用。需要按目标 profile 重新构建或使用兼容缓存，再经过输入与索引头检查激活。配置不匹配应返回实际状态，不能伪装成没有知识。

### 14. 引用如何保证正确？

系统保存笔记修订、小节、偏移、来源版本、原件 hash 与页码，并做支持和当前性检查。这提供身份与定位约束。当前小节级证据仍可能不足以支持每句归纳，引用正确性需要独立评测。

### 15. 删除笔记后，向量立即物理删除吗？

先让内容失去当前查询资格，再构建和激活不含失效 Chunk 的索引代。旧矩阵和缓存可以保留为历史，物理清理另行管理。关键是旧内容不能继续作为当前证据返回。

### 16. Worker 崩溃和旧任务迟到怎样处理？

新 Worker 领取有效租约，校验冻结 profile 与检查点后继续。发布再次核对租约、版本、输入和代次，过期结果被拒绝。远端请求的回执丢失仍可能导致重复计费，需要有限重试和回执追踪。

### 17. 40.5% 降幅能说明什么？

它说明固定四份 PDF 的历史对照中，文本 Token 从 996,515 降到 592,536。没有独立盲式质量 A/B，也未完全控制缓存与重试条件，因此不能推广为所有资料的费用降幅或质量提升。

### 18. 目前最需要改进的地方是什么？

知识质量和合并规则。优先建立主题、公式、图片与引用支持的标注集，再量化重复、错合并、净新增遗漏和导入顺序影响。音视频接入需要增加转写与时间证据，仍是后续扩展方向。
